# 허브 공급·긴급발주 기능

현재 `main`의 `hub-service/hub_service.py`에 있는 일 단위 FEFO 로직을
`app/features/SPEC.md`에 맞춰 API 기능으로 연결했습니다.
브랜드 UI와 세 가지 시연 계정을 연결했습니다. 공통 입력은 기본값을 유지하며 확장했습니다.
`app/main.py`, 기존 엔진과 독립형 서비스의 계산식은 수정하지 않습니다.

## API와 공통 계약

`POST /api/hub`는 기존 `app.core.scenario.Scenario`만 받습니다.

```json
{
  "as_of": "2026-09-15",
  "store_id": "S02",
  "horizon_days": 7,
  "demand_multiplier": 1.2,
  "delay_days": 1,
  "service_level": 0.95
}
```

- `feature.py`: `Hub` 선언. registry가 라우트를 자동 생성합니다.
- `schemas.py`: `HubResponse(BaseResponse)`와 `Row` 기반 표 행입니다.
- `service.py`: 공통 데이터와 예측을 연결하고 응답을 만듭니다. FastAPI를 import하지 않습니다.
- `planner.py`: 수량·로트·공간·차량·대안 탐색의 순수 계산입니다. 원본 파일을 읽지 않습니다.
- `settings.py`: 매장 수, 허브 수 상한, 30분 경로, 보관 여유 공간, 차량, 비용 등 운영 가정입니다.
- `test_hub.py`: 이 기능에 한정된 계약·수량 보존·정보 시점·긴급발주 테스트입니다.

데이터 접근은 `app.core.data.table()` 및 `open_orders()`만 사용합니다.
수요는 공통 `app.forecast.Forecaster`의 EWMA·요일·공휴일·행사 보정을 사용하고,
확정 수요를 BOM으로 식자재 소요량으로 변환합니다. 허브에서 예측 수요를 임의로 할인하지 않습니다.
예측 기간 확장은 이 기능 내부의 하위 클래스로 처리합니다.

## 계산 흐름

1. 전일 마감 로트와 기준일 전에 발주한 미입고분을 읽습니다. 당일·미래 발주는 사용하지 않습니다.
2. 첫 입고 전 부족과 입고 후 부족을 FEFO로 구분합니다. 정기발주는 입고 후 부족과 안전재고를 보충합니다.
3. 무허브와 허브 대안에 동일한 예측·잔차 블록·안전재고 원기준을 적용합니다.
4. 허브가 있으면 매장 안전재고 일부를 모으되, 실제 해당 경로의 준비·이동·수령 시간만큼 로컬 보유 하한을 둡니다.
5. 허브 수·매장 묶음을 탐색하고, 30분 도달·입고 직후 최대 보관량·일일 차량 여력을 검사합니다.
6. 선택 대안에서 정기발주와 허브 공급을 계산한 후, 다음날 이후에 남은 부족만 외부 긴급발주 초안으로 제공합니다.

매장 간 직접 이동과 허브 간 이동은 이 기능에서 실행하지 않습니다.
허브→매장 공급만 모델링합니다. 실제 주문·예약·승인·정산도 실행하지 않습니다.

## 응답: 프론트 담당자 연결 지점

프론트에서는 공통 시나리오로 `apiPost('/api/hub', scenario)`를 호출하면 됩니다.
UI는 `frontend/src/pages/OperationsPage.tsx`에서 이 API를 사용합니다.

| 필드 | 의미 |
|---|---|
| `scenario`, `assumptions` | registry가 채우는 공통 입력과 계산 가정 |
| `conditions` | 실제 사용한 허브 운영 가정. 입력 필드가 아닙니다. |
| `alternatives` | 허브 0개 포함 비용·식자재 충족률·제약 통과 여부 |
| `groups` | 선택 대안의 허브·매장 묶음·보관 및 차량 검사 |
| `store_orders`, `hub_orders` | 매장 및 허브 정기발주 초안 |
| `transfers` | 허브→매장 공급 수량과 원래 소비기한 |
| `emergency_orders` | 이후 미해결 부족에 대한 외부 긴급발주 초안 |
| `shortages` | 긴급발주 반영 전 남은 부족. 오늘의 부족도 별도 확인 가능 |
| `warnings` | 최소 발주금액 검토, 시간 해상도 등 실제 결과의 한계 |

수량은 사용 단위, 발주는 정수 포장 단위, 금액은 원 단위 정수,
충족률은 0~1입니다. 모든 표 행에 `basis`가 있습니다.
`status=NO_FEASIBLE_PLAN`이면 `groups` 등은 실행 추천이 아닌 진단 대안입니다.

`hub_store_ids`로 계산에 포함할 매장을 지정합니다. 미지정 시 기존 3개 매장을 유지합니다.
시연에서는 S01/S02만 허브 범위에 들어가며, S03은 단독으로 계산합니다.
허브 담당자는 그룹 발주를, 소속·독립 매장은 자신의 행만 봅니다. 이는 시연용 화면 분리이며 서버 인증 권한은 아닙니다.
`horizon_days`를 넘지 않는 범위에서 품목별 다음 보충 입고 경계까지만 비교합니다.
후속 발주를 아직 모델링하지 않은 날짜를 품절로 집계하지 않습니다.

## 운영 가정과 제한

기본은 매장 3개, 허브 상한 2개, 편도 30분, 준비 10분·수령 5분,
허브당 냉장/냉동/상온 순여유 200/200/150L, 차량 1대·일 360분입니다.
기본 배송 추가비는 0원이며 실제 운임이 주어진 것이 아닙니다.
실측 포장 부피가 없어 단위 환산 가정을 사용합니다.

보관 여유 공간·허브 운영비·회당 운송비는 공통 Scenario 입력으로 연결했습니다.
`hub_policy=assigned`는 전체 지정 그룹을 H01에 고정하며, 제약에 실패해도 무허브로 몰래 전환하지 않습니다.
`auto`는 무허브 포함 대안을 탐색하고, `none`은 허브 개수를 0으로 제한합니다.
허브 자체 매장 경로는 0분, 나머지는 편도 30분 가정입니다.
4개 이상 매장은 제공 3개 매장의 복제 시나리오입니다.

안전재고는 기준일 전에 결과가 확정된 잔차 블록의 분위수입니다.
동일한 블록을 여러 매장에 함께 적용해 수요 상관을 유지합니다.
정기발주 최소금액 미달은 `MIN_AMOUNT_REVIEW`이며 입고로 간주하지 않습니다.
긴급발주 초안은 소비기한·보관량 검토 전이며 충족률에 개선 효과를 합산하지 않습니다.
다음날 입고로 오늘의 판매손실을 회복했다고 표시하지 않습니다.

일 단위 수량 모형으로 동시 배차 대기와 분 단위 품절 방지를 보장하지 않습니다.
충족률은 원가 가중 식자재 지표로 메뉴 판매율과 다릅니다.
비용은 합성 가격의 자원비·보유비·배송비·허브비·미충족 페널티이며 실제 절감액이 아닙니다.
기존 독립 엔진의 발주량·백테스트 결과가 이 기능의 성과를 검증한 것은 아닙니다.
