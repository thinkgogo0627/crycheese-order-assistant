팀 전달문 — 식자재 정기발주와 지역 허브 운영 비교 서비스
작성일: 2026-10-31

1. 서비스가 하는 일

제공된 3개 매장·16개 메뉴·22개 식자재 데이터에 수요예측, 소비기한을 반영한 재고 전망, 정기발주, 허브 비축량 산정, 매장 그룹 배정, 제약·비용 비교를 연결했다.

운영 원칙은 다음과 같다.
“매장은 공급사에 정기발주한다. 선정된 일부 품목의 추가 필요량은 가까운 허브에서 보충한다. 일반 매장끼리 직접 이동하지 않는다. 허브를 사용하지 않는 안도 함께 비교한다.”

실행 코드는 hub_service.py 하나다. Python 3.10 이상 표준 라이브러리만 사용한다. 웹 화면과 HTTP API, 계산 엔진이 모두 이 파일에 들어 있다. 원본 ZIP/CSV는 코드에 포함하지 않는다.

2. 데이터 연결과 정보 경계

01 매장 / 02 메뉴 / 03 식자재 / 04 BOM / 05 공급사 / 06 가격 / 09 판매 / 11 발주 / 15 메뉴 취급 / 16 로트 재고를 읽는다.
12 실제 입고나 당일 마감 재고를 미래 정보로 추천에 넣지 않는다. 기준 시각은 선택한 날짜의 06:00 Asia/Seoul이다. 재고는 전일 기말 로트, 확정 입고는 기준일 이전에 발주한 건만 사용한다. 당일 오전 실사 오차는 아직 알 수 없는 정보로 처리한다.

수요예측은 첨부 train.py의 mean7 / weekday4 / blend를 표준 라이브러리로 계산한다. 7월 h=0~3 WAPE로 평균 후보 중 매장별 모델을 선택한다. 결과는 S01 blend, S02 mean7, S03 mean7로 재현됐다. HGB 두 후보의 학습·가중치·전체 5후보 선택을 재현한 것은 아니다. 따라서 이 파일을 원본 train.py 전체의 대체물로 설명하지 않는다.
7월 선택 결과를 미래 정보로 쓰지 않도록 서비스 기준일은 2026-08-01~09-30으로 제한한다.
메뉴 잠재수요를 BOM으로 환산할 때 과거 28일 취소율을 별도로 보정한다. 세트는 자체 BOM을 한 번만 적용한다. 메뉴 취급 계획은 사전에 알려졌다고 가정한다. 데이터 종료 뒤 짧은 예측은 마지막 취급 상태를 유지한다.

3. 전체 계산 순서

입력 → 매장별 예측 → 공급사별 현재/다음 입고 경계 → 로트 FEFO 전망 → 매장 기본 발주 → 감축률별 매장 발주 조정 → 과거 오차 블록으로 그룹 보충 요청 재현 → 허브 발주 산정 → 유한한 허브 재고로 다시 배분 → 보관/배송/소비기한/최소금액/충족률 검사 → 허브 수별 비용 비교 → 추천 또는 실행 가능한 안 없음 표시.

매장 발주:
- 기본 안전재고는 과거 보충 기간의 예측 오차 분위수를 이용한다. 팀의 안전재고 값으로 대체할 수 있다.
- 허브 이용 품목은 기존 안전재고×(1−감축률)을 후보로 사용하되, 예상 준비·이동·수령 시간을 버틸 최소량보다 낮추지 않는다.
- 예측 수요 자체를 줄이지 않는다. 소비기한과 제때 도착하는 확정 입고를 고려해 포장 전 순필요량을 구하고, 포장 단위 및 최소수량으로 올린다.
- 정기발주 최소금액 미달 시 MIN_AMOUNT_REVIEW로 남긴다. 불필요한 상품을 넣어 금액을 채우지 않으며, 이런 발주를 확정 입고처럼 사용하지 않는다.

허브 발주:
- 예측 오차는 매장별로 독립 섞지 않고 같은 과거 날짜 블록을 함께 사용한다. 같은 날 여러 매장이 바빠지는 현상을 유지한다.
- 각 매장의 양수 보충 요청을 합산한다. 일반 매장끼리 이동하지 않으므로 다른 매장의 음수 오차로 부족을 임의 상쇄하지 않는다.
- 새 허브 입고 이후~다음 허브 입고 경계 전 요청량의 선택 분위수로 목표량을 잡는다. 예상 요청량과 불확실성 대비분이 이미 포함된 분위수에 안전재고를 중복 추가하지 않는다.
- 허브 기존 로트는 신규 입고 전 출고 가능량을 보수적으로 차감한 뒤 반영한다. 실제 수량·만료일 배분은 다시 시뮬레이션한다.
- 허브 자체 영업 재고는 일반 매장 재고로 유지한다. 입력하는 허브 재고·보관 용량은 공동 비축 전용분이다.

공급사 조건:
- A: 일~금 정기발주 / 17시 전 / 익일 입고 / 최소금액 120,000원.
- B: 일·화·목·금 정기발주 / 16시 전 / 익일 입고 / 최소금액 없음.
- delivery_days 컬럼을 note보다 우선한다. 기준시각은 06시여서 당일 마감 이전이다.
- 데이터 명세서상 긴급발주는 요일·마감·최소금액 예외이며 다음날 07시 입고다. 허브 발주 모드를 emergency로 바꾸면 이 합성 운영 조건을 적용한다. 실제 업체의 계약상 권리라는 뜻은 아니다.
- 현재 놓친 판매는 내일 발주량으로 다시 더하지 않는다. 향후 부족만 긴급발주 초안으로 만들며, 포장 올림에 따른 소비기한·보관 검토 상태로 남긴다. 초안은 실제 예약·발주가 아니다.

4. 허브 수와 그룹 구성

- 허브 후보는 H01~H03이다. 실제 주소가 아니라 “공동 비축 공간을 확보할 수 있는 후보”다.
- 기본 이동시간은 각 후보에서 각 매장까지 편도 30분이라는 가정이다. 모든 경로가 같으면 지리적 입지 우열을 알 수 없으며, 그룹은 주로 공간·배송·비용 차이로 결정된다.
- 고급 입력 matrix로 후보별 매장 이동시간을 바꿀 수 있다. 30분 초과 경로를 포함한 그룹은 실행 가능으로 추천하지 않는다.
- 모든 매장은 직접발주 유지 또는 하나의 허브 그룹에만 배정된다. 한 매장을 두 허브에 중복 배정하지 않는다.
- 매장 6개 이하는 허브 미사용/일부 매장 사용, 그룹 분할, 후보 허브 배정, 감축률 후보를 탐색한다. 입력된 후보와 감축률 격자, 현재 수량 모형 안에서의 탐색이지 모든 현실적 운영 방식의 전역 최적화는 아니다.
- 7~12개는 근사 그룹 구성을 비교한다. 최적해 보장은 없으며 결과에 bounded_greedy_grouping으로 표시한다.
- 제공된 실매장 프로필은 3개뿐이다. 4개 이상 입력하면 V04 등 가상 매장을 만들어 원래 3개 프로필·재고를 반복 사용한다. 실제 추가 매장 데이터가 아니며, 같은 프로필의 과거 오차도 함께 움직인다. 매장이 늘었다는 이유로 독립적인 수요 분산 효과를 만들어내지 않는다.

5. 보관·배송 제약과 비용

냉장/냉동/상온별로 입고 직후 최대 점유 부피를 계산해 공동 비축 순여유 공간과 비교한다. 평균·마감 잔량만 보지 않는다. 용량을 넘으면 발주량을 몰래 잘라 실행 가능한 것처럼 만들지 않는다.
부피는 품목별 ‘발주 포장 1개의 L’를 입력받는다. 기본 부피는 설명용 가정이다. 특히 g·ml를 포장 부피로 단순 환산한 기본값은 실제 실측값으로 바꿔야 한다. 기본 보관 한도 200/200/150L도 실측값이 아니다.
소분 기본값은 금지다. 서로 다른 로트의 개봉 잔량을 합쳐 온전한 한 포장으로 간주하지 않는다. 소분이 실제로 허용되는 환경에서만 split_allowed=true를 사용한다. 이동 시 원래 로트의 마지막 사용일을 유지한다.
여러 품목을 같은 매장에 같은 날 보내면 한 번의 배송으로 묶고 고정 운송비를 한 번 계산한다. 차량별 하루 작업시간을 넘기지 않도록 검사한다. 준비·수령 시간을 포함하므로 30분 이동=30분 보충 완료는 아니다.

비교 지표는 구매 현금, 종료 재고·미도착 구매자산, 폐기 원가, 배송비, 허브 운영비, 보유비, 원가기준 식자재 수량 충족률이다. 서로 다른 g·ml·개를 그냥 합산하지 않는다.
경제비용은 시작재고+기존 확정입고+신규구매−종료자산으로 자원 사용비를 구한 뒤 보유비·배송비·허브비·미충족 원가 페널티를 더한다. 폐기는 자원 수지에 들어 있으므로 다시 중복 가산하지 않는다. 실제 회계 이익이나 메뉴별 판매손실을 계산한 것은 아니다.
품목별 다음 보충 입고 경계까지만 동일 조건으로 비교한다. 다음 발주를 아직 모델링하지 않은 이후 날짜를 ‘보충이 없어서 품절’로 잘못 세지 않는다. 결과 horizon.item_end_exclusive에 각 품목의 경계를 기록한다.

6. 서비스 실행

Python 3.10 이상에서 다음을 실행한다. 패키지 설치는 필요 없다.

python hub_service.py --data "제공 데이터 ZIP 전체 경로"

또는 CSV가 들어 있는 data 폴더를 지정한다.

python hub_service.py --data "CSV 폴더 전체 경로"

브라우저 주소: http://127.0.0.1:8765
다른 포트: --port 8766
종료: 실행 중인 터미널에서 Ctrl+C
기본 테스트: python hub_service.py --self-test
시나리오 파일을 읽어 화면 없이 결과 저장:
python hub_service.py --data "데이터.zip" --config scenario.json --report result.json

서비스는 localhost에서만 접속한다. 원본 ZIP/CSV를 공개하는 경로는 없다. 원본을 공개 GitHub에 넣지 않는다.

7. 팀 통합용 API

GET /health : 서버 상태
GET /api/meta : 데이터 해시·선택 모델·기본 입력
POST /api/plan : 아래 형식의 JSON을 받아 전체 비교 결과 반환

최소 예:
{
  "as_of": "2026-09-01",
  "store_count": 3,
  "max_hubs": 2,
  "travel_minutes": 30,
  "service_target": 0.95,
  "alpha_grid": [0, 0.25, 0.5],
  "capacity_liters": {"chilled": 200, "frozen": 200, "ambient": 150}
}

팀의 식자재 예측 연결:
forecast_overrides = {"S01": {"I016": {"2026-09-01": 700, "2026-09-02": 750, "2026-09-03": 700}}}
단위는 식자재 use_unit이다. 해당 요청의 결과 horizon 범위에 속한 모든 날짜가 필요하며, 누락된 날짜를 0으로 간주하지 않는다. 메뉴 예측이라면 BOM과 취소율 보정을 담당한 팀 모듈에서 식자재 소요량으로 바꾼 뒤 전달한다.

팀의 안전재고만 연결:
baseline_safety_overrides = {"S01": {"I016": 200}}

팀의 기존 발주 계산 결과까지 연결:
baseline_order_overrides = {
  "S01": {
    "I016": {
      "basis": "NET_NEED_INCLUDES_SAFETY",
      "net_need_before_pack_qty": 1500,
      "safety_qty": 200,
      "horizon_end_exclusive": "2026-09-03"
    }
  }
}
이 순필요량에는 매장 재고와 확정입고 차감, 기존 안전재고가 이미 반영돼 있어야 한다. 서비스는 이를 다시 차감하지 않고 안전재고 변화분만 교체한 뒤 포장을 올린다. 포장 수만 보내면 원래 순필요량을 알 수 없으므로 연결 입력으로 쓰지 않는다. 날짜 경계가 다르면 오류를 반환한다. 같은 매장·품목에 안전재고 override도 넣었다면 baseline_order_overrides의 값이 우선한다.

경로 입력:
matrix = {"H01": {"S01": 10, "S02": 30, "S03": 55}, "H02": {"S01": 40, "S02": 20, "S03": 15}}
이 예에서 H01–S03과 H02–S01은 공급권 밖이다. 생략한 경로는 travel_minutes 기본값을 사용한다.

허브 초기 로트:
hub_stock = {"H01": {"I016": [{"qty": 1000, "last_use_date": "2026-09-05"}]}}
qty는 use_unit 기준이다. 기본 허브 초기 재고는 0이다. 신규 발주가 도착하기 전부터 재고가 있는 것처럼 계산하지 않는다.

주요 출력:
- recommended: 제약과 목표를 만족한 비용 최소 후보. 없으면 null.
- diagnostic: 가장 가까운 검토 후보. recommended 대신 실제 실행안처럼 사용하지 않는다.
- alternatives: 허브 개수별 비교.
- selected_details: 매장 그룹, 매장 발주, 허브 발주, 시나리오별 충족률·최대 보관량·기준수요의 이동·미해결 부족.
- emergency_drafts: 내부 보충과 정기입고를 반영한 후에도 남는 향후 부족의 긴급발주 초안.
- source: 입력 해시와 예측 선택 정보.
- assumptions: 데이터와 모형의 해석 범위.

기존 단일 에이전트에는 plan(data, payload) 또는 POST /api/plan을 하나의 읽기 전용 도구로 연결한다. 숫자는 계산 결과를 사용하고, 설명 모델이 발주량을 임의 생성하지 않는다. 실제 승인·예약 기능은 별도 트랜잭션으로 구현해야 한다.

8. 제공 데이터 실행 결과와 검증

기본값(2026-09-01, 3매장, 30분, 순여유 공간 200/200/150L, 운송 5,000원/회, 허브 12,000원/일, 정기 허브 발주)에서는 허브 없는 안이 선택됐다.
원가기준 수량 충족률은 허브 없음 약 99.69%, 허브 1개 후보 약 99.74%였다. 허브 1개 후보는 소폭 더 공급했지만, 입력한 운영비·운송비를 반영한 비교 비용이 더 높았다. 이 수치는 현재 가정의 한 번의 재고 스냅샷 비교이며 장기 절감 효과나 실제 브랜드 성과가 아니다.
허브가 유리한 결과를 강제로 만들지 않는다. 용량·비용·그룹·수요 배율·초기 재고를 바꿔 동일 조건에서 재계산한다.
핵심 함수 테스트 12개, 실제 데이터·API 통합 테스트 16개를 실행했다. FEFO·마지막 사용일·로트 보존·개봉 잔량 합치기 금지·미래 데이터 차단·미래 발주 제외·용량·30분 경로·중복 배정 방지·최소금액·오늘 손실 재주문 금지·자원비 수지·품목별 기간 경계·팀 발주량 이중 차감 방지를 확인했다. HTTP 정상/잘못된 입력 응답도 확인했다. 브라우저 자동 연결 문제로 실제 화면의 시각적 QA는 완료하지 못했고, 클라이언트 스크립트는 별도로 검사했다.

9. 구현 범위와 다음 단계

이 버전은 일 단위 FEFO 수량과 비용으로 허브 운영안을 비교하는 실행 가능한 계획 서비스다. 과거 오차 시나리오의 서비스 목표는 실제 95% 서비스 보장을 뜻하지 않는다. 같은 자료로 안전재고를 산정하고 제약을 점검하는 조건부 실험이므로 별도 시점의 순차 검증이 필요하다.
30분은 경로 제한이며 실제 분 단위 보충 보장이 아니다. 동시 주문의 배차 대기, 다중 경유, 차량 적재 부피, 운송 중 온도 측정, 매장 냉장고 용량, 품질·조리 실수 폐기는 아직 모형에 포함하지 않는다. 소분 허용, 실제 포장 부피, 출고 담당자 확보는 현장 확인 값이다.
다음 단계는 팀의 예측/발주 모듈을 위 입력 계약에 연결하고, 실제 후보 위치·교통시간·온도대별 순여유 공간·운송 견적을 입력한 뒤 기간을 이동하며 비교하는 것이다. 실제 발주 실행은 승인·버전·중복 요청 방지·재고 예약을 추가한 뒤 연결한다.
