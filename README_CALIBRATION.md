# 시간대별 예측 통합 안내

기준: 사용자가 제공한 `hackathon_cry_cheese-main.zip`. 현재 GitHub 원격 HEAD와 같다고 가정하지 않는다.
기존 모듈형 서버에 첨부 최적화 소스의 시간대별 모델을 이식했다. 기존 `app/engine.py`, `app/forecast.py`, `app/lot_projection.py`, `app/main.py`는 유지했다.

## 포함 기능과 API

- 화면: `/intraday` — 매장, 판단일, 정각 판단시각, 전망시간, 수요배율, 예측 프로필, 보정 강도 변경 시 API 재계산.
- `POST /api/hourly_forecast`: 완료된 POS 시간만 차례로 관측하여 다음 시간 메뉴 수요와 BOM 소요를 계산.
- `POST /api/intraday_plan`: 이전 영업일 lot에서 재구성한 재고로 시간대별 부족과 실험적 매장 이동을 비교. 실제 이동·발주를 실행하지 않는다.
- 기존 일별 발주 화면·API와 예측 모델은 그대로 유지한다. 시간대별 프로필을 바꿔도 기존 일별 모델을 교체하지 않는다.

구현은 `app/features/hourly_forecast/`에 격리했다. 관련 두 API가 같은 계산 모듈을 공유한다. 공통 변경은 Scenario 입력 확장, registry 등록, `CRY_DATA_DIR` 경로 일치, 프런트 메뉴·타입 연결이다. 기능 폴더 밖 변경을 제한한 기존 팀 규약에 대한 통합 예외이므로 PR에서 이 파일들을 함께 검토한다.

## 시간과 데이터 계약

일별 기준 `as_of`는 판단일 아침이다. 기본 예측은 전날까지의 `demand_qty`를 사용하고, 시간대별 보정만 판단일 `decision_time` **이전에 종료된 시간**의 `max(qty-cancel_qty, 0)`를 추가로 사용한다. 판단일 마감재고·미래 실제 판매·미래 실제 입고로 재고를 보정하지 않는다.

9월 30일 영업 종료 기준의 일별 계획은 `as_of=2026-10-01`이다. 이 날짜에는 기록된 POS가 없으므로 화면이 9월로 몰래 바꾸지 않고 날짜 변경 버튼을 표시한다. API는 확정 `live_sales`가 없으면 422를 반환한다.

`live_sales`는 매장·메뉴·시간별 **전체 확정 스냅샷**이다. 누락은 0으로 간주하며 부분 전송을 지원하지 않는다. 중복, 미완료 시간, 음수·비유한 수량을 거부한다. 빈 배열은 확정 판매 0이며 과거 기록으로 대체하지 않는다. 실시간 POS 수집 연동 자체는 구현하지 않았다.

## 최적화와 검증

시간대 분포 중복 계산을 줄이고 기본예측은 최대 24개 시나리오를 캐시한다. 원본 설정 파일은 1회 읽고 호출자에게 복사본을 제공한다. 변경된 CSV나 설정은 서버 재시작 후 반영한다. 이 변경의 속도 개선 비율을 별도로 측정하지 않았으므로 수치로 주장하지 않는다.

첨부 파라미터는 `config/selected_params.json`에 보관한다. `original`, `balanced`, `protective`를 비교할 수 있으며 protective는 과소예측 손실 가중치 1.5라는 가정이다. 실제 영업 손실비율을 뜻하지 않는다.

2026-08-01~09-30, 활성 매장×메뉴×시간 29,036건, 첫 영업시간 제외, `sum(abs(pred-demand_qty))/sum(demand_qty)` 기준으로 고정 파라미터를 재생했다. 결과는 동봉 검증 보고서에 기록한다. 이 데이터는 반복 열람되었으므로 독립적인 최종 검증셋이나 실제 운영 성과로 해석하지 않는다. 기존 대화의 **일별 평균 모델 WAPE 26~28%대와는 평가 단위·방법이 다르다.** 이번 재생으로 그 수치까지 검증한 것은 아니다.

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest -q
python scripts/evaluate_hourly.py
cd frontend
npm ci
npm run build
npm run lint
```

`evaluate_hourly.py`는 실제 시간대별 계산 클래스로 고정 설정만 평가하고 `work/hourly_evaluation.json`에 집계 결과를 쓴다. 전체 탐색은 `python scripts/tune_hourly.py`로 실행하며 `work/hourly_tuning/`에 저장한다. 서비스 설정을 자동 덮어쓰지 않는다. 탐색은 7월을 사용하지만 8~9월 결과를 보고 반복 수정하면 별도 미래 기간 검증이 필요하다.

## 실험적 이동 기능의 제한

초기 A·B·C 범위에서 제외했던 이동은 첨부 소스의 선택적 실험 화면으로만 제공한다. 핵심 일별 발주를 대체하지 않는다. 30분 이동, 사용단위 소분 가능, 동시 운송 가능, 다음 날 수요 40% 보호를 가정한다. 이는 실측 또는 운영 승인 조건이 아니다. 서비스 수준·일별 전망일수·기존 소분 토글은 이 이동 계산에 적용되지 않는다. 이동비 입력은 예상 비용 표시에 반영되지만 경로의 경제 최적화에는 사용하지 않는다. 지연일은 예정 입고 재구성에 반영한다. 기한 지난 미입고는 판단일 도착으로 가정하며 확정 재고가 아니다.

실시간 재고·운송 제약이 확정되기 전에는 이동 추천을 실행 지시로 사용하지 않는다. 합성 데이터와 가상 단가의 예상 개선량이며 실제 폐기·품절 절감 실적이 아니다.

## 데이터와 배포

패키지에는 원본 CSV를 포함하지 않는다. 기존 비공개 저장소의 `data/raw/`를 유지하거나 서버의 `CRY_DATA_DIR`로 제공한다. `.gitignore`는 이미 추적 중인 CSV를 제거하지 않는다. 이 패치는 기존 데이터를 삭제하지 않는다.

서버는 현재 구조상 원본 CSV가 필요하다. README의 processed-only 방향은 아직 이 기능의 실제 실행 방식이 아니다. 기존 Vercel 구성을 유지하며 기능 코드 안의 JSON이 배포에 포함되어야 한다. 원격 배포와 브라우저 E2E는 별도 확인 단계다. 프런트와 API는 같은 브랜치 버전으로 배포해야 한다.
