# S02 폐기 로트 추적과 선택적 조정

팀 통합 엔진 α=1.6의 부족 감소를 유지하면서 S02 양상추(I009)·코울슬로(I017)·식빵(I020)의 폐기를 줄일 수 있는지 검토했다. 기준 소스는 `6758477`. 이동 비용은 사용자 조건에 따라 **0원**이다. 원본 데이터가 아니라, 같은 합성 수요 경로에서 정책별로 재전개한 재고의 결과다. 금액은 가상 원가다.

## 먼저 읽을 결론

- 폐기가 발생한 S02 세 품목의 발주 로트 47건에서는 **공급사 최소금액 증량이 0**이었다. 안전재고 보충과 포장 올림, 이후의 예상보다 작은 수요가 먼저 확인할 대상이다. 이 47건이 전체 발주의 원인 분포를 대표하지는 않는다.
- 예측 폐기가 줄어드는 주문만 한 포장 줄이는 탐색안은 전체 기한폐기 **494,307→389,243원**, 미판매 **19.568→15.315개**였다. 전 매장·메뉴·날짜별 미판매 증가도 없었다. 그러나 주문 시점의 예측 부족을 늘리지 말라는 제약까지 넣으면 감량은 **0건**이다. 실현 경로에서는 좋았지만 예측 기준의 안전성이 확보된 정책은 아니다.
- 양상추만 예방 이동하면 기한폐기 **430,347원**, 미판매 동일. 효과는 **3월 S02→S01 3회**에 집중되고 8~9월 기한폐기 개선은 없다. 조건부 사건 대응 후보로 보존한다.
- 코울슬로 이동은 S01 미판매를 늘렸고, 식빵 이동은 전체 기한폐기를 늘렸다. 세 품목을 묶어 상시 이동하는 정책은 채택 근거가 부족하다.
- 앱에는 **임박 수량 / 해당 로트의 예상 사용 / 예상 폐기**를 구분하는 출력을 반영했다. 선택적 감량·예방 이동 실험은 이 폴더에서 비교하며, 기본 발주 α=1.6을 자동 교체하지 않는다.

## 1. 어느 주문에서 폐기가 나왔나

`baseline`은 기존 정기발주와 긴급발주를 유지하고 장중 이동의 미래 수요 참조만 당시 예측으로 바꾼 비교 기준이다. 1월부터 전개하고 2~9월을 집계한다.

| S02 품목 | 기한폐기 가상 원가 | 폐기 로트/날짜 | 발생 월수 | 해당 주문량 중 예상 부족 보충 | 안전재고 보충 | 포장 올림 | 최소금액 증량 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 양상추 | 149,206 | 4 / 4 | 2 | 12.4% | 66.0% | 21.6% | 0% |
| 코울슬로 | 49,352 | 16 / 16 | 6 | 0.0% | 53.6% | 46.4% | 0% |
| 식빵 | 46,500 | 27 / 27 | 8 | 3.8% | 56.9% | 39.3% | 0% |

분해는 발주 계산의 회계적 분해다. 발주 직전 다음 정기입고 전까지 FEFO로 예상 부족·남는 재고를 계산하고, 부족 보충→안전재고 보충→포장 올림→최소금액 증량 순으로 주문량을 배분했다. **폐기된 개별 단위가 안전재고 때문이었다는 인과 증명이나, 위 비율만큼 폐기를 줄일 수 있다는 뜻은 아니다.** 사용기한 상한에 의해 주문이 제한되면 실제 기본 주문량까지만 각 항목을 배분한다. 감량 시에는 증량→올림→안전재고→부족 보충의 역순으로 차감해 수지를 맞춘다.

폐기 로트의 주문별 입고일부터 사용기한까지 예상 수요와 사후 수요를 비교하면, 세 품목 모두 해당 창의 예측 합계가 더 컸다. 창이 겹칠 수 있고 폐기된 주문만 고른 표본이므로 전체 모델의 예측 오차율로 해석하지 않는다. 사후 수요는 원인 설명에만 쓰며 감량·이동 의사결정에 넣지 않는다.

각 로트는 주문 근거, 입고량, 실제 사용량, 품질폐기, 소비기한 폐기, 이동 후 도착 매장, 기말 잔량까지 연결된다. 이동해도 원래 로트 ID와 사용기한을 유지한다. 전 로트에서 `입고량 = 사용 + 품질폐기 + 기한폐기 + 기말잔량`을 검증했다.

## 2. 전체 정책을 유지한 대안 비교

아래는 전 매장·전 품목 합계다. 감량 및 예방 이동 대상만 S02의 세 품목으로 제한한다. 품절 건수는 매장×재료×날짜이고, 미판매는 메뉴 수량이며 모형의 부분 충족 때문에 소수일 수 있다.

| 2~9월 대안 | 기한폐기 | 전체 폐기 | 미판매 메뉴 | 품절 건수 | 미판매가 늘어난 매장×메뉴×일 |
|---|---:|---:|---:|---:|---:|
| 비교 기준 `baseline` | 494,307 | 2,245,430 | 19.568 | 3 | 0 |
| 매 주문 한 포장 감량 `trim_one` | 234,849 | 1,959,430 | 431.209 | 23 | 71 |
| 예측 폐기 감소 주문만 감량 `trim_expiry` | 389,243 | 2,138,782 | 15.315 | 3 | 0 |
| 위 감량 + 예측 부족 비악화 `trim_point_guarded` | 494,307 | 2,245,430 | 19.568 | 3 | 0 |
| 위 감량 + 수요 120% 부족 비악화 `trim_guarded` | 494,307 | 2,245,430 | 19.568 | 3 | 0 |
| 세 품목 예방 이동 `transfer_guarded` | 421,084 | 2,171,914 | 23.422 | 3 | 3 |
| 양상추만 이동 `transfer_I009` | 430,347 | 2,182,133 | 19.568 | 3 | 0 |
| 코울슬로만 이동 `transfer_I017` | 482,555 | 2,232,723 | 23.422 | 3 | 3 |
| 식빵만 이동 `transfer_I020` | 496,794 | 2,247,917 | 19.568 | 3 | 0 |

`combined`는 수요120% 감량 보호와 세 품목 예방 이동을 결합한 안이며 감량이 없어 `transfer_guarded`와 같다. `trim_one`은 위험 확인용 비교로, 2~9월 552건의 주문에서 감량되어 대상 주문을 더 좁혀야 함을 보여준다.

`trim_expiry`는 2~9월 **50건(양상추3·코울슬로11·식빵36)**에서 한 포장씩 줄였다. 공급사 최소금액·품목 최소수량은 유지한다. 8~9월만 보면 기한폐기 **104,058→98,199원**, 전체폐기 **523,050→516,203원**, 미판매 **9.439개로 동일**하다. 이 기간 구매액은 오히려 **4,000원 증가**했다. 구매 감소와 폐기 절감을 같은 지표로 취급하지 않는다.

양상추 이동은 2~9월 기한폐기를 약 **63,960원** 줄였지만 8~9월에는 104,058원으로 동일했다. 후반 전체 폐기는 약427원 증가했다. 코울슬로는 후반만 보면 개선되지만 전 기간 S01 미판매가 늘어 통과시키지 않았다. 품절 건수가 같아도 미판매 수량은 달라질 수 있다.

### 의사결정 규칙과 시간 순서

- 정기발주: 07시 입고 반영 후 기존 엔진 호출. 전체 안전재고 α=1.6, 공급사 일정·최소금액·포장 제약 유지. 감량은 대상 주문당 최대 1포장.
- `trim_expiry`: 주문안과 1포장 감량안을 같은 날짜별 예측으로 전개해 기한폐기가 줄어들 때만 감량. 예상 부족 증가를 별도로 막지는 않는 **탐색안**이다.
- `trim_point_guarded`/`trim_guarded`: 위 조건에 기본 수요/수요120%의 날짜별 예상 부족 비악화 조건을 추가. 이 자료에서는 실행0건. 향후 정기발주를 모두 포함한 재계획 전망은 아직 없으므로 보수성이 과도할 수 있다.
- 예방 이동: 사용기한이 7일 내인 S02 로트 중 **수요120%에서도 남는 물량**만 후보. 수령점은 **수요80%에서도 기한 내 부족한 만큼**만 받고, 14일 전망에서 수령점 예상 폐기가 증가하지 않아야 한다. 제공점 날짜별 예상 부족도 증가하지 않아야 한다. 80/120%는 민감도 가정이며 확률 구간이 아니다.
- 예방 이동은 개점 전 09시 출발·09:30 도착, 사용 단위 소분 허용, 원래 사용기한 유지, 비용0원이다. 다른 정책의 발주 전 단계에서 선반영하므로 정기발주량도 다시 계산된다. 실물 경로·이동 중 재고·인력 제한은 미모형화했다.
- 기존 장중 부족 대응 이동은 현재 시간의 이미 관측된 주문 + 이후 시간의 예측, 제공점의 남은 시간 예측 + 과거 사용량 완충으로 판단한다. **장중 즉시 도착** 가정은 기존 비교와 같으며 실제30분 운송 재현이 아니다.

## 3. 앱에 연결한 산출물

`app/lot_projection.py`는 메뉴별 판매 가능량을 BOM의 모든 재료로 함께 제한하고 FEFO로 소비한다. 패티가 없으면 해당 버거의 빵·양상추도 사용되지 않는다. 같은 기한은 입고일 순으로 처리하며 입력 재고를 변경하지 않는다.

`expiry` 알림의 기존 `qty`는 임박 로트 전체량으로 유지했다. 추가 필드는 다음과 같다.

| 필드 | 의미 |
|---|---|
| `expiring_qty` | 오늘부터 3일 내 마지막 사용일에 도달하는 현재 로트 수량 |
| `expected_use_before_expiry_qty` | 그 로트들에서 기한 내 실제로 사용할 것으로 예상한 수량 |
| `expected_expiry_qty`, `expected_expiry_cost` | 그 로트들에서 기한 끝까지 남을 예상 수량·기준일 단가 평가액 |
| `lots[]` | 로트 ID, 입고일, 마지막 사용일, 현재량, 예상 사용·폐기, 날짜별 수지 |
| `projection_basis` | 메뉴 결합, 기확정 입고만 포함, 신규 발주·이동 전의 전망임을 표시 |

이 알림에는 오늘 이후 새 발주·이동·품질폐기를 포함하지 않는다. 따라서 연속 운영 백테스트나 화면의 모든 정책을 실행한 후 폐기액과 같을 필요가 없다. 메뉴 우선순위는 기존 앱처럼 공헌이익 순이며 최적 판매 배분 해법이 아니다.

`ingredients`에는 `opening_stock`, `received_today`, `current_stock`, `inventory_basis`를 제공한다. `current_stock`을 알림과 같은 **07시 입고 후·실사/이동 전 장부수량**으로 맞췄다. 발주 응답의 `need_components`는 예상 부족, 필요한 안전재고 보충, 포장 올림, 최소금액 증량을 제공한다. 소분 공동발주에서는 매장별 계산 근거이며, 최종 공동 배분량과 합산 일치한다고 가정하지 않는다.

정적 `/dashboard`와 React 재고 화면 모두 임박·사용·폐기를 나눠 표시한다. API/두 UI의 기본 이동 비용은0원이다. 사용자가 비용을 입력하는 기존 시나리오 기능은 유지한다.

## 재현과 검증

저장소 루트에서, 원본17개 CSV는 로컬 `data/raw` 또는 `CRY_DATA_DIR`에 둔다.

```bash
pip install -r requirements.txt pytest httpx
python tools/waste_refinement/study.py --output ../waste_study_local
python tools/waste_refinement/summarize.py ../waste_study_local --output ../waste_study_local/aggregate_results.json
python -m pytest tests -q
cd frontend
npm ci
npm run build
npm run lint
```

- 게시된 `aggregate_results.json`: 집계 수치·매장별 검증·발주 분해·월별 반복성. 원본/주문·로트 상세행은 포함하지 않는다.
- 로컬 `<variant>_lots.json`, `<variant>_events.json`, `summary.json`: 원인 추적과 재검증용 상세 출력. 공유 저장소에 추가하지 않는다.
- `oracle_reference`: 기존 장중 실제 미래 수요를 쓰는 모드. 원본 팀원 시뮬레이터의 미판매/품절/기한폐기/품질폐기/구매/재고 배열과 최대차이0을 확인했다. 기존 **2,392,063원·3건·기한폐기487,704원**은 이 참조 모드의 수치다.
- 전 로트 수지 최대오차는 약 `1.46e-11` 사용 단위. 미래 당일·이후 실제 수요를 변경해도 이동용 남은 시간 예측이 같은지 테스트한다.
- 원래8개+신규9개 테스트, React TypeScript/Vite 빌드 검증. lint는 기존 Fast Refresh/배열 key 경고가 남는다.

## 해석의 한계와 다음 단계

이것은 이미 여러 번 살펴본 기간의 탐색이다. 8~9월 수치는 별도 기간 점검이며 새로운 미관측 검증이 아니다. 수요는 합성 잠재 주문 `demand_qty-cancel_qty`이고 실제 매장에서 그대로 관측할 수 있다고 가정할 수 없다. 품질폐기는 냉장 잔량의 하루0.3% 모형이며 실제 보관/조리 원인을 해결한 성과가 아니다.

기존 공헌이익·일부 안전재고 계산은 전체 가격 이력 평균의 영향을 받는다. 이번에 제거한 정보 참조는 **장중 이동의 미래 실제 수요**이며, 엔진 전체의 모든 정보 누수를 해결했다고 주장하지 않는다. 기존 `run_robust.py`의 누락 모듈과 이전 강건성 결과는 여기서 재검증하지 않았다. 새 실험 결과를 기존 화면 이동 함수나 독립 `hub-service`의 성능으로 사용해서는 안 된다.

다음 우선순위는 (1) 예상 폐기 알림과 로트 근거로 조치 후보를 보여주기, (2) `trim_expiry`에 향후 발주 재계획·수요오차를 넣어 안전성을 다시 확인하기, (3) 양상추의 특정 과잉 사건에서만 이동 후보를 보조적으로 표시하기다. 선택적 발주와 이동을 실제 자동 추천으로 채택할지는 이 검증을 거쳐 결정한다.
